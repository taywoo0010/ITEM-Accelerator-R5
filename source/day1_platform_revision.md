### D1.3. 平台架构、产品全景与能力底座｜讨论时段沿用原议程

本节保留原有三页：参考演示 04 的七层架构、参考演示 05 的产品全景，以及知识挖掘与能力底座补充。在第三页之后保留六页补充，采用 [ITEM Enterprise AI Platform v2](https://tommyyula.github.io/item-ai-plateform-v2/) 的通用平台主线，介绍企业问题、Knowledge Fabric、本体、共用架构、Factory、Marketplace、ItemGPT 与客户接入，共九页，讨论时段沿用原议程。[参考演示：product_general_investor_v4.3](https://tommyyula.github.io/item-ai-strategy/product_general_investor_v4.3)。产品名称和原稿验证状态作为参考定位，不等于这些能力已经在 ISS 开通或集成；新增六页不依赖特定业务系统，以工单、SOP 和资料分析为示意；产品材料描述与 ISS 实际接入、权限、部署和验收分开说明。

#### D1.3.1 七层平台架构：五层核心产品 + 两层开放集成

第 1 层和第 7 层是客户已有基础设施与终端系统，不是 ITEM 产品。ITEM 的核心产品集中在第 2–6 层；通过开放接口连接现有业务系统，不重复建设客户的系统和硬件。

| 层 | 作用 | 产品／集成映射 |
|---|---|---|
| 7 · 开放集成 | 终端与物理执行：已有应用、设备、机器人、POS、门店与现场系统 | 任意品牌机器人／IoT／POS／移动端；MCP、A2A、API、PLC |
| 6 · 核心产品 | 行业模板：行业对象、流程、规则与智能体的可插拔方案 | ItemChain、ItemFin、ItemDine、ItemEstate、ItemBuild 等 |
| 5 · 核心产品 | 通用 AI 应用：跨行业共用的决策、执行、预测、支持与增长能力 | ItemGPT、ItemClaw、ItemFlow、ItemSense、ItemPredict 等 |
| 4 · 核心产品 | 企业运营平台：应用构建、工作流编排与人机协同工作区 | Item Foundry、Item AI OS |
| 3 · 核心产品 | AI 运行时：多模型编排、Agent、治理与合规审计、部署 | Item AIP、Blackbox Router、Harness |
| 2 · 核心产品 | 数据与语义智能：对象、关系、规则、状态和业务上下文 | Item Ontology、GraphRAG、Digital Twin |
| 1 · 开放集成 | 客户已有云、本地与边缘算力及存储 | AWS、Azure、GCP、私有云、本地、边缘 |

核心内核共用，行业差异通过模板和配置承接。ISS 的具体接入范围、权限、接口和部署责任仍需与业务及 COO AI Team 对齐。

#### D1.3.2 产品全景：12 个通用应用 × 10 个行业模板

**Layer 5 · 通用应用：**ItemGPT、ItemClaw、ItemFlow、ItemSense、ItemPredict、ItemOps AI、ItemAudit、ItemVision、ItemVoice、ItemSupport、ItemGrow、ItemDoc。

**Layer 6 · 行业模板：**ItemChain、ItemDock、ItemTrade、ItemFin、ItemDine、ItemEstate、ItemBuild、ItemHealth、ItemAuto、ItemRetail。

| 维度 | 通用应用（12） | 行业模板（10） |
|---|---|---|
| 回答的问题 | 企业运营需要哪些 AI 能力？ | 这些能力如何长成某个行业的样子？ |
| 复用方式 | 参考稿定位为跨行业 100% 复用，随平台交付 | 按行业加载，可组合、定制、由伙伴共建 |
| 研发经济学 | 一次构建，跨行业摊薄成本 | 首个模板成本最高，后续边际成本递减 |
| 销售角色 | 平台订阅的核心价值 | 行业切入点与溢价来源 |
| 验证状态 | 参考稿称已在供应链生产环境全量运行 | 参考稿将 ItemChain 标为已验证，其他按已验证机制复制 |

以上保留参考演示 05 的产品结构，不将“产品全景”理解为 ISS 本轮需要全部购买、开放或重新开发的范围。落地重点是复用已有产品，配置业务对象与规则，适配接口，补齐必要扩展和测试。

#### D1.3.3 能力底座：优先复用既有成果

- **Data Hub：**统一事实和上下文，保留来源、时间、版本、权限及业务定义。
- **Model Hub / Hybrid AI：**大模型用于理解与协作，小模型处理稳定高频任务，预测与优化模型承担相应计算；按任务评测、路由和复用，不因某个场景有价值就立即自建模型。
- **Connector / Tools / Skill：**标准连接与受控查询、行动，明确输入输出、权限、失败处理、版本和 Owner；Runtime、Agent、Workflow 承接使用，Factory 承接评测、发布与日志。
- **Marketplace / Dashboard：**前者登记、发现、组合和治理能力；后者观测采用、质量、成本与实际业务结果，不以登记量或调用量替代价值。

在 COO AI Team Hollis 的 Accelerator 框架支持下，优先对齐已有数据、模型、算力、工具与治理成果；成熟度、授权和接口以本轮能力对齐为准。

#### D1.3.4 知识挖掘的四种起点

| 起始材料 | 首要工作 | 形成什么 |
|---|---|---|
| CSR ticket | 归类问题、动作、结果与例外 | 问题优先级与 Agent 候选 |
| 业务数据与代码 | 识别字段、结构、规则与系统约定 | 候选业务本体、分析页与应用结构 |
| WIKI、UKM、SOP | 核对定义、有效版本、条件和缺口 | 小本体、规则、样本与 Skill |
| 视频／录屏与真实操作 | 提取步骤、判断、跨系统活动和例外 | 经审核 SOP、Workflow 或 Agent 草案 |

**真实来源 → 提取 → 业务／专家审核 → 对象、关系、规则、Action → 场景样本验证 → 发布与反馈。** 按任务复杂度选择规则、小本体或完整建模，不要求每个任务先建大型本体。

#### D1.3.5 发布与持续演进的最低要求

原始记录、AI 草稿、审核知识和已发布规则分开；业务 Owner 确认定义、例外及有效期。变更经过正常、异常及独立样本回归，再授权发布；保留版本、日志、反馈和回滚。业务状态回写与知识／能力反馈分别管理，客户敏感资料及未审核推断不自动成为产品资产。

#### D1.3.6 企业 AI：贯通知识、能力与业务执行

[ITEM Enterprise AI Platform v2](https://tommyyula.github.io/item-ai-plateform-v2/) 将企业知识、能力建设、受控执行与持续复用组织在同一个平台中。客户面对的通常不是单纯“缺少一个大模型”，而是知识散落、业务含义不一致、回答与行动脱节，以及单项目成果难以复用。

Knowledge Fabric 汇集文档、SOP、工单、视频、代码与数据，保留业务来源；Ontology 定义对象、关系、规则与上下文；Agent Factory 将需求组织成可测试和发布的 Agent / Team；Runtime 承接运行；Marketplace 与 ItemGPT 让能力可发现、可授权、可组合并进入用户日常工作。

用通用服务工单说明用户价值：“请依据服务 SOP，分析这张工单并准备处理建议。”这是面向客户的任务示意，不是 ISS 已完成集成的案例。相同底座可用于知识服务、资料分析、客户沟通与审批协作，具体动作仍取决于数据、接口与授权范围。

长期资产是企业自身知识、本体、Skill、运行记录和改进经验；底层模型是可按任务替换的执行资源。本版不采用平台网页中缺少统计口径的知识占比、试点转生产比例或重复成本倍数，也不以业务系统实例数论证客户适用性。

#### D1.3.7 Knowledge Fabric：把业务材料变成可执行知识

[平台材料的 Knowledge Fabric 与 Ontology 章节](https://tommyyula.github.io/item-ai-plateform-v2/) 描述多模态知识输入和业务可读的建模过程：不是只将文件放进检索库，而是形成可以查询、验证并交付 Agent 使用的语义资产。

其内容覆盖对象与实例、关系、规则、状态、例外、Action 及证据链。业务人员使用熟悉的文档和材料共建；来源与数据绑定支撑真实上下文。CQ（Competency Question，能力问题）题树定义本体需要回答的问题，题库、Recall Profile、Issue 和专家反馈帮助定位覆盖缺口与质量问题。

页面给出的生命周期为：明确目标与 CQ → 补充真实业务上下文 → 顶层设计 → 扫描来源并构建业务本体 → 问题与样本验证 → 通过 Skill、MCP、A2A 和受限令牌交付。六页中把这一路径概括为目标、建模、验证、交付四步；按任务复杂度选择规则或小本体，不要求先建设全企业大型本体。

客户可以先使用一组服务 SOP、典型工单、合同条款或业务样例验证小范围定义。业务材料更新后进入知识与本体演进流程，审核、验证和发布要求沿用 D1.3.5；不把未审核推断自动变为已发布规则。

#### D1.3.8 一套共用架构：入口、能力、语义与执行分工

[新版平台的 Architecture 章节](https://tommyyula.github.io/item-ai-plateform-v2/) 采用四层协作视图，说明产品如何共同运行；它与前面七层产品全景互补，不是替换原有产品分层，也不表示客户需要重建四套系统。

- **L4 用户入口：**ItemGPT、Personal Assistant、协作渠道与嵌入式页面接收意图、发现专业 Agent、组织协作并展示结果。
- **L3 能力生产：**Agent Factory / Steward、Agent IDE、Skill Factory 与 AI Marketplace 承接 Agent / Team 构建、测试、发布、发现、订阅与计量。
- **L2 语义与知识：**Ontology Studio、Ontology Runtime、Knowledge Fabric 与 Dataset Sources 组织本体、数据绑定、来源、版本、Action 和验证。
- **L1 执行底座：**Agent Runtime / Temporal、Connector、Model Gateway、Tool Gateway 与 VFS 承接持久执行、凭据和触发器、模型路由、工具调用、文件与记忆上下文。

平台材料描述 MCP 用于能力和工具暴露，A2A 用于 Agent 发现、委派与回调，API 用于连接既有应用；Tool Gateway 可将 OpenAPI / Swagger 转成 AI 工具，Model Gateway 承接配额、故障切换以及按应用、租户、用户或 Agent 归因的用量和成本。客户已有系统保留业务事实与权威执行责任。

这里引用的是产品页面描述的能力与架构，不是 ISS 部署证明。具体连接、身份权限、凭据、模型与生产运行责任仍需与客户环境对齐。

#### D1.3.9 Agent Factory：从业务需求到受控发布

[Agent Factory 与 Architecture 章节](https://tommyyula.github.io/item-ai-plateform-v2/) 将自然语言意图转成建设、测试、发布和持续改进流程。先明确角色、工作流、预期结果与约束，连接本体、业务规则和上下文，使输入输出与完成条件可检查。

Steward 组合既有知识、Skills、Tools、APIs 和 MCP 能力，形成 Agent 或 Team。多 Agent 任务由主 Agent 分解，专业 Agent 分工，使用共享上下文、会话与产物；需要升级和人工介入时保留责任边界。

材料描述在批准的参数、端点和管理凭据下测试，使用 IAM / RBAC、受限令牌、配额和审计约束访问。多 Agent 运行包含步骤追踪、失败归因和人工审批机制；人工可进行单次或会话确认，也可拒绝。ISS 的正常、异常、权限及高风险测试要求在实际范围中确认，不以生成了一段指令代替系统控制。

通过审核的能力发布到 Marketplace，供 ItemGPT 发现调用。Runtime 的持久执行、网关的模型与工具管理、用量与成本归因，以及运行记录和反馈支撑后续优化。具体控制粒度、恢复方式、接口副作用和生产发布要求须按客户环境确认；不将产品页面的架构描述当成客户环境已全部启用。

#### D1.3.10 Marketplace + ItemGPT：发现、组合与复用能力

[Marketplace、ItemGPT 与 Training 章节](https://tommyyula.github.io/item-ai-plateform-v2/) 将 Agents、Skills、MCP Servers、APIs 和 Tools 组织为能力资产。Marketplace 的作用不只存放代码，而是让用途、输入输出、示例、Owner、版本、可见性及使用边界明确。

团队可以发布、搜索、试用、订阅和绑定能力，配置权限、凭据与配额；能力按选定团队、企业或 Marketplace 范围共享。ItemGPT 从业务意图出发调用专业 Agent，结合本体、Skill 和工具组织多 Agent 协作，不要求用户自行了解全部后端连接。

服务工单的通用示意是：读取附件 → 按服务规则理解问题 → 专业 Agent 准备回复或调用系统 → 人工确认关键动作、保存结果和运行记录。该示意用于说明机制，不声称已接入 ISS 的工单系统或审批流程。

使用者检查来源、执行状态与异常，保存、分享、导出结果并给出反馈。建设与运营人员管理升级、依赖、兼容性、下线、审批和审计记录。换场景后仍要验证术语、规则、数据映射、权限、接口副作用、样本与 Owner；共享能力不等于共享所有客户数据或自动获得写权限。

#### D1.3.11 客户接入：复用产品、配置集成、按角色推广

本轮面向客户的实施重点是复用既有平台、知识、Agent、Skill 和运行能力，配置业务对象与规则，集成客户已有系统，并完成必要扩展和测试，而不是从零研发另一套平台。对接路径结合[新版平台 Training 章节](https://tommyyula.github.io/item-ai-plateform-v2/) 与 D1.4 / D1.5 的实施和责任边界。

业务专家提供授权材料、规则与样本，确认定义和业务完成标准；业务用户检查来源、结果与异常，确认或接管关键动作。ITEM / FDE / 建设者配置本体、Skill、工具和流程，设计测试、发布、版本维护与资产沉淀。COO AI Team 按需对齐数据、接口、身份权限、模型、部署和治理，保留现有系统，不成为所有业务探索的前置入口。

培训按职责组织，不要求人人掌握全部工程模块。业务专家与使用者重点学习 Knowledge Fabric 的材料与语义共建、ItemGPT 的目标表达和结果检查；建设者重点学习 Agent Factory 的构建、测试、诊断与发布，Marketplace 的登记、授权、升级和复用；运营与企业支撑人员学习相关权限、配额、审计、维护与接管要求。

建议接入路径为：①确认材料、场景、Owner 与业务基线；②复用已有对象、规则、Agent 和 Skill 并进行配置；③对齐接口、权限、异常与人工确认，授权集成和试运行；④按业务结果、质量和净成本验收，并配套培训与反馈。可以从服务工单、知识服务或资料分析等候选任务讨论输入，具体场景和系统范围由客户确认。

该路径是待共同确认的实施建议，不预设 ISS 已上线或承诺特定周期、费用及节省比例；不增加原议程时长，衔接 D1.4 的验收边界和 D1.5 的七阶段共建。

### D1.4. 落地与验收边界｜讨论时段沿用原议程

旧风险与平台融合内容浓缩为一张补充页，不再为未定义的内部产品名词单独展开。

1. **先复用，再配置与集成。**保留既有业务系统和用户入口，盘点知识、模型、Agent、Skill 和接口。能直接用就复用，差异通过配置、适配及必要扩展解决；不先重写平台。
2. **行动有权限和责任。**查询和 Action 均受授权约束，高风险动作需要人工确认。区分生成建议、调用成功与业务执行成功；两类回写分别留痕，可追踪、可回滚。
3. **独立证据决定上线。**覆盖正常、异常、边界、缺失信息及权限场景，关注高风险失败，不只看平均正确率。保留引用、澄清、拒答、转人工、版本及失败分类。
4. **按流程结果和净成本验收。**先定业务基线、统计范围和 Owner，比较完成率、周期、返工、服务承诺和单位成本；计入算力、维护及人工审核，不以 Agent 数量或调用量证明价值。

**输出：**复用与集成清单、受控行动边界、质量与价值基线、Owner 和下一步，作为 D1.5 的实施输入。会议目的不是寻找一个 Hero 案例，而是通过多组实践形成 ISS 的整体转型蓝图、共用能力及可持续实施路线。

### D1.5. 思考：针对 ISS 的实施｜1 小时，衔接 Day 2

#### D1.5.1 合作计划：职责、能力对齐与七阶段共建

本节把前面的案例、平台能力和风险原则映射到 ISS：从哪里开始，哪些能力构成可持续的长期优势，和谁共建，以及下一决策门是什么。第一天形成初步判断，不在企业能力、真实业务材料和责任尚未对齐前，提前锁定第二天的最终实施决定。

##### C. 三部门联合开发，COO AI Team 按需支撑

| 参与方 | 主要责任 | 不应被替代的责任 |
|---|---|---|
| **ISS Biz (team)** | 场景、流程、规则、专家、业务数据定义、验收、采用和价值验证 | 不能把业务规则及价值判断全部交给 IT 或 AI。 |
| **COO AI Team** | ITEM 的直接对接团队；Hollis 方法框架、已有 AI/数字化成果、模型/底座与治理支撑；在企业数据、源代码、现有软件、接口、跨部门功能、基础设施、安全与认证需要时按需支撑 | 不能把未确认的接口、资源或未来能力当作已交付；支持按需进入，不成为所有业务探索必须先经过的统一入口。 |
| **ITEM** | 场景落地、FDE 协作、Agent/Workflow/页面工程、能力编排、测试、产品化与交付 | 不能绕过企业权限、业务审核和生产上线要求。 |

每个场景明确三方 Owner、FDE、专家审核人、系统与数据责任人、审批人及运营维护人。人员可以兼任，责任字段不能缺失。

##### D. 与 AI Accelerator 对齐能力与协作边界

在 **COO AI Team Hollis 的 Accelerator 理论框架支持下**，ITEM 与 Accelerator 是互补关系：ITEM 聚焦业务应用、体验、Agent/Workflow、动态页面与产品化；Accelerator 提供可复用企业能力、服务化与治理支撑；ISS Biz 定义场景与验证业务价值。

##### 七阶段总图：业务轴 × 功能轴 × 实施路径

在逐阶段展开前先对齐总图。**业务轴**定位真实业务流程、角色、服务对象、价值指标与 Owner；**功能轴**识别知识与检索、分析与决策、编排与执行等跨流程可复用能力。两轴交点定义任务，不是选一个 Hero 案例。分类示意不是已批准的场景或已完成的集成。

| 业务轴（示意） | 知识与检索 | 分析与决策 | 编排与受控执行 |
|---|---|---|---|
| 客户服务／CEC | 工单、知识、上下文 | 分类、路由、判断 | 派发、转人工、回写 |
| BO／备件与服务承诺 | 库存、规则、客户承诺 | 替换、优先级、预测 | 审批、订单与状态更新 |
| 仓储／物流／现场服务 | SOP、数据、操作记录 | 异常诊断、资源优化 | Workflow、通知与接管 |

**知识挖掘 → 能力底座 → Agent／流程共建 → 培训普及 → 优化与垂直深耕 → 沉淀产品 → 复制推广。** 共用底座在不同业务流程中反复使用；每阶段有材料、Owner 和验收门，才决定继续、调整或停止。后面的七页逐阶段展开这条路径，不代表本轮自动承诺全部完成。

##### G. 哪些能力形成长期优势

围绕已确认案例与既有成果讨论：共同业务语义、经过专家审核的知识与规则、可复用的连接和行动接口、稳定评测与闭环数据、应用工程能力，以及跨场景持续维护的组织机制。长期优势应体现为更可靠的业务结果、较低的重复建设成本和更快的跨场景交付，而不是仅以 Agent 数量、模型归属或某一个聊天入口判断。
