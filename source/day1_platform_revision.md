### D1.3. 平台架构、产品全景与能力底座｜讨论时段沿用原议程

本节保留原有三页：参考演示 04 的七层架构、参考演示 05 的产品全景，以及知识挖掘与能力底座补充。在第三页之后增加六页，将前面案例中的业务结果、任务链、架构机制、执行控制、复用资产与验证边界连接起来，共九页，讨论时段沿用原议程。[参考演示：product_general_investor_v4.3](https://tommyyula.github.io/item-ai-strategy/product_general_investor_v4.3)。产品名称和原稿验证状态作为参考定位，不等于这些能力已经在 ISS 开通或集成；新增内容区分 WMS 本地实现、其他案例呈现与 ISS 待验证事项。

#### D1.3.1 七层平台架构：五层核心产品 + 两层开放集成

第 1 层和第 7 层是客户已有基础设施与终端系统，不是 ITEM 产品。ITEM 的核心产品集中在第 2–6 层；通过开放接口连接现有业务系统，不重复建设客户的系统和硬件。

| 层 | 作用 | 产品／集成映射 |

| 7 · 开放集成 | 终端与物理执行：已有应用、设备、机器人、POS、门店与现场系统 | 任意品牌机器人／IoT／POS／移动端；MCP、A2A、API、PLC |
| 6 · 核心产品 | 行业模板：行业对象、流程、规则与智能体的可插拔方案 | ItemChain、ItemFin、ItemDine、ItemEstate、ItemBuild 等 |
| 5 · 核心产品 | 通用 AI 应用：跨行业共用的决策、执行、预测、支持与增长能力 | ItemGPT、ItemClaw、ItemFlow、ItemSense、ItemPredict 等 |
| 4 · 核心产品 | 企业运营平台：应用构建、工作流编排与人机协同工作区 | Item Foundry、Item AI OS |

核心内核共用，行业差异通过模板和配置承接。ISS 的具体接入范围、权限、接口和部署责任仍需与业务及 COO AI Team 对齐。

#### D1.3.3 能力底座：优先复用既有成果

- **Data Hub：**统一事实和上下文，保留来源、时间、版本、权限及业务定义。
- **Model Hub / Hybrid AI：**大模型用于理解与协作，小模型处理稳定高频任务，预测与优化模型承担相应计算；按任务评测、路由和复用，不因某个场景有价值就立即自建模型。
- **Connector / Tools / Skill：**标准连接与受控查询、行动，明确输入输出、权限、失败处理、版本和 Owner；Runtime、Agent、Workflow 承接使用，Factory 承接评测、发布与日志。
- **Marketplace / Dashboard：**前者登记、发现、组合和治理能力；后者观测采用、质量、成本与实际业务结果，不以登记量或调用量替代价值。

在 COO AI Team Hollis 的 Accelerator 框架支持下，优先对齐已有数据、模型、算力、工具与治理成果；成熟度、授权和接口以本轮能力对齐为准。

#### D1.3.4 知识挖掘的四种起点

| 起始材料 | 首要工作 | 形成什么 |
|---|---|---|
| CSR ticket | 归类问题、动作、结果与例外 | 问题优先级与 Agent 候选 |
| 业务数据与代码 | 识别字段、结构、规则与系统约定 | 候选业务本体、分析页与应用结构 |
| WIKI、UKM、SOP | 核对定义、有效版本、条件和缺口 | 小本体、规则、样本与 Skill |
| 视频／录屏与真实操作 | 提取步骤、判断、跨系统活动和例外 | 经审核 SOP、Workflow 或 Agent 草案 |

**真实来源 → 提取 → 业务／专家审核 → 对象、关系、规则、Action → 场景样本验证 → 发布与反馈。** 按任务复杂度选择规则、小本体或完整建模，不要求每个任务先建大型本体。

#### D1.3.5 发布与持续演进的最低要求

原始记录、AI 草稿、审核知识和已发布规则分开；业务 Owner 确认定义、例外及有效期。变更经过正常、异常及独立样本回归，再授权发布；保留版本、日志、反馈和回滚。业务状态回写与知识／能力反馈分别管理，客户敏感资料及未审核推断不自动成为产品资产。

#### D1.3.6 平台价值：把业务请求变成可验证的结果

平台介绍应从业务任务出发，而不是重复列举产品。以 D1.2.2.2 的破损库存案例为例：巡检员请求上报破损，Agent 生成 Dynamic Task，系统校验照片等必填信息；提交后创建 Inventory Issue，货况 Good → Damaged，库存不可拣。主管通过 Dynamic Page 汇总并确认派工，以本人权限创建 Move Damage 任务，Issue 由 Open 变为 In Progress。执行人复用 Move Inventory 标准步骤，扫码核对并按策略放入 DMG-01；两条 Issue 自动变为 Resolved。操作人、库存流水、来源页面和版本能够追溯。

这条链的结果不是“表单已生成”，而是业务状态经过检查后发生变化并留有记录。上述机制在 ITEM WMS 本地环境实现；演示动画、人物和单据号为示意，不代表 ISS 已上线或完成基线测量。

Rate & Quote（D1.2.3.8）用数据语义和价格规则支持分析、模拟与报价，最终批准与计费关联按实际范围说明；AVL（D1.2.4.8）用同一供应商本体支撑查询分析与动态页面。两例作为平台能力路径的依据，不据此推断已完成任意生产系统集成或取得量化收益。

#### D1.3.7 三类工作面，承接同一条任务链

Ontology Studio 面向业务 Owner、专家与共建者，定义对象、关系、规则、流程和 Action 边界，结合数据语义审核有效范围。Agent Factory 面向 FDE、Senior User 和 Developer，将本体、接口及规则组织为可测试、可调用的 Agent、Workflow 和工具能力，承接测试、审核和发布。ITEMGPT Runtime / ItemGPT 面向业务用户与一线人员，让用户用自然语言提出需求，使用 Agent 与动态页面，并在自己的权限内试用、确认和执行。

共同任务链是：明确问题、角色与完成条件 → 取得对象、规则及授权数据 → 调用或生成能力，按需试运行和发布 → 系统校验、执行、状态与反馈。不是每次查询都要重新生成并发布应用，也不是所有任务都必须经过同一种开发方式。

WMS 的实际分工是 Agent 理解与生成，WMS 执行权限、库存和业务规则，有权限的人决定发布和关键动作。三类工作面沿用 D1.1.2；执行机制依据 D1.2.2.3，语义到能力的路径依据 D1.2.3.4–7。不能把用户代理写成拥有全权的自动执行者。

#### D1.3.8 业务语义、执行能力与系统接口如何连接

承接 D1.3.1 的七层架构，用前面案例说明各层责任，而不新增另一套产品目录。业务含义由 Item Ontology、Ontology Studio 及 Object Database / Data Hub 组织，包含对象、关系、规则、数据语义与上下文；Rate Sheet 和 AVL 为语义到应用的案例依据。

能力建设由 Agent Factory、Agent / Workflow 及 Dynamic Task / Dynamic Page 等承接，使用本体、接口目录和标准动作。WMS 生成巡检任务和派工页面，不另写一套库存逻辑，也不绕过既有接口。运行与交互映射到 ITEMGPT Runtime、Item AIP / Harness、Model Hub、Connector / Tools，承接模型与工具调用和运行管理；具体模型、托管、计量及治理范围以目标环境能力对齐为准。

WMS、BNP、AVL 等客户既有系统保留权威业务事实、权限校验与 Action 执行。客户已有云、本地和现场终端通过接口集成；不要求重建系统或迁移全部 Agent。这是依据 D1.3.1 / D1.3.3 与案例组织的责任映射，不代表 ISS 已开通全部产品或接口。

#### D1.3.9 生成可以灵活，权限与发布必须受控

以下控制依据 D1.2.2.3 的 ITEM WMS 本地实现，不能直接外推为 ISS 已通过安全认证或所有平台环境已采用同一沙箱。

用户委托令牌不是超级用户令牌。接口检查角色权限、仓库范围与任务归属，用户不能做的，Agent 也不能做。Dynamic View 的只读取数代码按内容哈希不可变保存，在 WebAssembly 沙箱运行；无文件系统、无环境变量、不能访问其他网络，只拿当前用户的只读令牌。

生成与上线分开：草稿仅作者可见，经过试运行和迭代，再由有权限的人发布。发布时预览接口所需权限；测试环境导出的定制包，导入生产后仍为草稿，不自动生效。变更记录关联操作人、来源页面、版本和库存流水；版本可以停用或回退。版本回退不等于自动撤销已经发生的库存或业务动作，业务补偿须按实际系统规则处理。

ISS 接入时需要重新验证身份与权限映射、只读沙箱适配、生产发布职责以及日志追踪范围，不能只用 Prompt 中的安全要求代替系统控制。

#### D1.3.10 复用业务语义、标准动作和发布资产

复用对象不仅是一整个 Agent。业务语义层可以复用本体、对象与规则结构、接口目录；标准动作层可以复用 Task Context / Lines / Records 三层存储与 Composable Step；应用层可以复用 Task Type、Dynamic Page 及定制包；验证与治理层可以复用版本机制、样本与回归方法以及异常记录。

具体例子是 Move Inventory 的 Take / Place，可用于组装、补货、库位优化和坏货处理。业务事实仍留在所属业务对象中，任务数据按三层结构引用，不因每个需求新增一张业务表。以上机制依据 D1.2.2.3；同一套本体支撑 Agent、分析页面与表单的案例依据 D1.2.3.7。

换场景仍须重验业务术语与客户规则、货况和库位映射、接口副作用、角色和任务权限、目标环境依赖、样本分布、风险等级和完成标准，并明确维护 Owner。第一场景通过不能推断第二场景必然通过。

D1.3.3 中 Marketplace 是技术能力登记、发现和治理的定位，Dashboard 观察采用、质量、成本与业务结果。不能仅因有目录，就声称已实现跨团队订阅、完整版本兼容或规模化复用；实际共享范围和授权机制应以验证记录为准。

#### D1.3.11 已有实现与 ISS 验证，分开说明

WMS 本地已实现动态任务与页面、用户权限、只读沙箱、标准步骤、版本发布及变更留痕。Rate & Quote / AVL 案例呈现数据语义 → 本体 → 可调用 Agent → 分析与动态页面的路径；演示不能替代生产规模和收益证据。其实现范围分别依据 D1.2.2.1 / D1.2.2.3、D1.2.3.10 和 D1.2.4.8。

ISS 尚需确认数据、代码和 API 的可用范围，身份权限映射、测试与生产环境、真实执行／模拟／人工确认边界；同时需要正常、异常和权限样本、业务完成标准、Owner 与人工接管、基线和单位成本，以及跨场景复验记录。不给未确认事项标注 Production，也不移植其他平台的能力数量或规划阶段。

本轮建议以一个范围明确的任务通过四个验证门：①明确授权材料、场景范围与业务 Owner；②验证正常、异常及权限拒绝；③授权试运行并确认发布责任；④验收业务结果，复测质量和成本。这是待共同确认的验证方案，衔接 D1.4 的落地与验收边界，不增加原议程时长，不替代 D1.5 的完整七阶段路径。

### D1.4. 落地与验收边界｜讨论时段沿用原议程

旧风险与平台融合内容浓缩为一张补充页，不再为未定义的内部产品名词单独展开。

1. **先复用，再配置与集成。**保留既有业务系统和用户入口，盘点知识、模型、Agent、Skill 和接口。能直接用就复用，差异通过配置、适配及必要扩展解决；不先重写平台。
2. **行动有权限和责任。**查询和 Action 均受授权约束，高风险动作需要人工确认。区分生成建议、调用成功与业务执行成功；两类回写分别留痕，可追踪、可回滚。
3. **独立证据决定上线。**覆盖正常、异常、边界、缺失信息及权限场景，关注高风险失败，不只看平均正确率。保留引用、澄清、拒答、转人工、版本及失败分类。
4. **按流程结果和净成本验收。**先定业务基线、统计范围和 Owner，比较完成率、周期、返工、服务承诺和单位成本；计入算力、维护及人工审核，不以 Agent 数量或调用量证明价值。

**输出：**复用与集成清单、受控行动边界、质量与价值基线、Owner 和下一步，作为 D1.5 的实施输入。会议目的不是寻找一个 Hero 案例，而是通过多组实践形成 ISS 的整体转型蓝图、共用能力及可持续实施路线。

### D1.5. 思考：针对 ISS 的实施｜1 小时，衔接 Day 2

##### 七阶段总图：业务轴 × 功能轴 × 实施路径

在逐阶段展开前先对齐总图。**业务轴**定位真实业务流程、角色、服务对象、价值指标与 Owner；**功能轴**识别知识与检索、分析与决策、编排与执行等跨流程可复用能力。两轴交点定义任务，不是选一个 Hero 案例。分类示意不是已批准的场景或已完成的集成。

| 业务轴（示意） | 知识与检索 | 分析与决策 | 编排与受控执行 |
|---|---|---|---|
| 客户服务／CEC | 工单、知识、上下文 | 分类、路由、判断 | 派发、转人工、回写 |
| BO／备件与服务承诺 | 库存、规则、客户承诺 | 替换、优先级、预测 | 审批、订单与状态更新 |
| 仓储／物流／现场服务 | SOP、数据、操作记录 | 异常诊断、资源优化 | Workflow、通知与接管 |

**知识挖掘 → 能力底座 → Agent／流程共建 → 培训普及 → 优化与垂直深耕 → 沉淀产品 → 复制推广。** 共用底座在不同业务流程中反复使用；每阶段有材料、Owner 和验收门，才决定继续、调整或停止。后面的七页逐阶段展开这条路径，不代表本轮自动承诺全部完成。

##### E. 七阶段共建，边界先说清

| 阶段 | 主要工作 | 交付物与进入下一阶段的条件 |

可保留的产品化方向包括 ISS Service Intelligence、Back Order / Customer Promise、CEC / Genesys、Service Supply Chain Decision 与 WMS/Warehouse Business Tooling。具体名称、归属和优先级以验证结果为准。

##### F. 带入第二天的实施工作输入

第一天结束时，至少形成候选场景、待补材料、能力缺口、风险和责任清单；第二天按 D2.1–D2.4 深化，不重复完整的平台介绍：

1. 选一个候选场景，完成业务/功能分类和现状流程梳理。
2. 取一组可授权的真实材料，确认规则、样本和专家评审口径。
3. 明确数据、代码、知识、模型、接口和环境的可得性。
4. 起草小本体或 SOP/Workflow，划分自动、辅助、人工任务。
5. 完成首轮交付边界、评测要求与下一决策门。

以上工作分别进入 D2.2 的业务域讨论、D2.3.10 的资产沉淀、D2.3.20 的组织协作，并在 D2.5.10–D2.5.20 合并确认。第二天有独立完整议程，不再只是第一天未完成工作的备用时段；是否进行现场开发，仍由人员、授权、材料和环境准备决定，不能把工作坊讨论等同于已完成上线。

##### G. 哪些能力形成长期优势

围绕已确认案例与既有成果讨论：共同业务语义、经过专家审核的知识与规则、可复用的连接和行动接口、稳定评测与闭环数据、应用工程能力，以及跨场景持续维护的组织机制。长期优势应体现为更可靠的业务结果、较低的重复建设成本和更快的跨场景交付，而不是仅以 Agent 数量、模型归属或某一个聊天入口判断。

本段提出 Day 1 的初步判断，具体资产、技术选型、复用边界和责任在 D2.1–D2.4 验证，不预先替代真实场景和技术证据。
